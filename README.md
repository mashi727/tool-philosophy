# 道具は How である

## 中身は問いません

道具について、私はその中身を問わないことにしています。どういう仕組みで動いているのか、誰が作ったのか、新しいのか古いのか。そういうことは、あまり問題にしません。中身がよくわかっていなくても、同じことをすれば同じ結果が出るのなら、道具としては使えるからです。

その代わり、四つのことだけは厳しく問います。一つは、目的にかなう働きをするかどうか。二つ目は、何度やっても同じ結果が出るかどうか（再現性）。三つ目は、ほかの道具とうまくつながるかどうか（相互運用性と再利用性）。四つ目は、何をしたかの跡が残り、失敗したときに失敗したと正直に言うかどうか（来歴と、失敗の仕方）です。

あとの三つは、機械に調べさせることができます。けれども、最初の一つだけはそうはいきません。目的は、道具の中にはないからです。目的を持ち込むのは人間で、その判断の責任も、人間が負うほかありません。それでも、道具の側でできることはあります。人が決めたことに、使える範囲と出どころを付けておくことです。

この構図は、論理の妥当性が前提の正しさを保証しないのと、同じ形をしています。この点は別に論文として書きました[^1][^2]。ここでは、それが日々の道具づくりにどう現れたかをお話しします。

二つ目から四つ目を満たすための具体的なやり方は、ソフトウェアの世界がすでに用意してくれています。私はそれを、パラダイムごとに借りてきました。

## UNIX から ── 小さく作って、つなぐ

*三つ目の問い（つながるか）に応えるものです。*

**一つの道具には、一つの仕事しかさせません。** 録音を映像に合わせる道具を作ったとき、録音の止め忘れにも対応させようかと考えたことがあります。結局やめました。この道具は、同期を取ることだけに絞っています。めったに起きないことのために、ずっと複雑さを抱え込むのは割に合わないからです。

**受け渡しはテキストで行います。** 動画の章立ては、次のような数行のテキストにしています。

```
00:00:00 -- 開始前
00:14:09 001 Opening Tune
01:13:40 -- 休憩
```

人が読めて、どの道具からも読めます。先頭に `--` を付けた区間は、書き出すときに除かれます。

**書くのは、つなぎ目だけです。** 動画の処理は ffmpeg に、文字起こしは Whisper に、組版は LuaTeX に任せています。私が書くのは、それらをどうつなぐかだけです。車輪をもう一度発明する理由はありません。

## オブジェクト指向から ── 外から見た振る舞いだけを扱う

*一つ目と三つ目の問いに応えるものです。*

**界面は変えず、中身だけを差し替えます。** 文書の中の時刻の記法を書き換えたことがあります。すると、それを読んでいた別の道具で、動画の再生が止まってしまいました。同じ壊し方を、二度しています。いまは呼び出す側には手を付けず、記法の定義だけを差し替えるようにしています。形式を変える前には、誰がそれを読んでいるかを確かめます。

**道具は、出力で比べます。** 文字起こしのエンジンを、出力の文字数で比べたことがあります。最良に見えたエンジンの出力には、実際には存在しない発話が 21.3% 含まれていました。それを除いて比べ直すと、最良は別のエンジンで、その割合は 0.3% でした。中身ではなく、振る舞いを見るべきだったのです。

**差し替える場所は、一か所に閉じ込めておきます。** 無料で使っていた外部の言語モデルの基盤が、廃止されたことがあります。呼び出しを一つの関数に閉じ込めていたので、移行はその関数を直すだけで済みました。外部の基盤は、いつか消えるものと思っておくほうがよいようです。

## 関数型から ── 入力は変えず、出力は作り直す

*二つ目の問い（再現するか）に応えるものです。*

**元の資料は書き換えません。** 文字起こしの元の資料は、音声そのもの、単語ごとの時刻、来歴の三つにしています。字幕ファイルは、そこからいつでも作り直せる派生物として扱います。間違いを直すのも派生の側で、元には書き戻しません。来歴には、入力ファイルのハッシュまで残しています。

**どこで確定させるかを、決めておきます。** 長い録画では、章立てを人が確定させた時点を区切りにしています。それより前は、何度でもやり直せます。それより後ろの切り出しや字幕や記録は、すべてその区切りから作り直せば済みます。

**変わったところだけを作り直します。** 重い計算の結果は、入力の大きさと日付、それに道具の版を鍵にして保存しています。百ギガバイトを超える計測データでも、二度目からは二秒とかからずに開けます。

## 宣言型から ── やりたいことを一枚に書く

*三つ目と二つ目の問いに応えるものです。*

**手順ではなく、望む結果を書きます。** 映像と別撮りの録音から同期済みの映像を作るとき、私が書くのは一枚の設定ファイルだけです。何をどの順に処理するかは、道具が決めます。ただし、道具が下書きした設定には、必ず人が目を通します。

**数字は手で書きません。** 件数や割合を画面や文書に手で書くと、元の資料が変わったときに嘘になります。説明文も同じです。アンケートの分析画面で、手で書いた一行の説明が、二百件を超える集計の読み方を誤らせていたことがありました。二度とも、間違っていたのは説明文の側でした。

## 契約による設計から ── 前後の条件を確かめ、破れたら止める

*四つ目の問い（正直に失敗するか）に応えるものです。*

**終了コードが 0 でも、成功とは限りません。** ある文字起こしのモデルに語彙のヒントを渡したところ、結果は 0 件でした。それでも終了コードは 0 で、出力ファイルは 707 KB ありました。成功したように見える失敗が、いちばん危ないのです。いまは、中身を数えて確かめるようにしています。

**大量に動かす前に数え、動かした後で突き合わせます。** 168 本の動画の名前を一括で変える前に数えてみたら、無関係な 97 件が巻き込まれるところでした。別の作業では、成功 26 件と表示されたのに、実際のファイルは 24 本しかありませんでした。同じ名前で作られたファイルが、上書きされていたのです。いまは、対象と対象外を数え、旧名と新名の対応を先に書き出し、終わったら実際のファイル数と突き合わせています。

**合わなければ、組み立てを止めます。** 索引を作るとき、機械に「この箇所」と指させた語句が本文に見つからなければ、組み立てそのものを止めるようにしました。この仕組みが、指し間違いを 11 か所で捕まえてくれました。黙って通るより、止まるほうがよいのです。

## 追記型の履歴から ── 書き換えず、書き足す

*四つ目の問い（跡が残るか）に応えるものです。*

**触る前に、元を残します。** 観測や記述は、対象を変えてしまいます。触る前の状態は、あとから取り戻せません。そこで、アンケートの PDF は最初に開いたときに、配られた時点の原本を自動で退避するようにしています。出力先にすでにファイルがあれば止まり、上書きは、はっきり指示したときだけにしています。

**何をしたか、何をしなかったかを残します。** 作業のたびに、決めたことと、その理由を書き残しています。採らなかった案と、採らなかった理由も書きます。これがないと、同じ案を何度も検討し直すことになるからです。

## 決めたことには、範囲と出どころを付ける

*一つ目の問い（目的にかなうか）を、道具の側からできるところまで支えるものです。*

**何を区別するかは、計算では決まりません。** 章立てのテキストでは、曲と休憩を区別し、休憩には `--` を付けて書き出しから外しています。何を別のものとして扱い、何を同じものとみなすか。この選び方は、いくら計算しても出てきません。誰かが決めるしかないのです。しかも、選んだ表し方の良し悪しを、その表し方で計算した結果で測ることはできません。循環してしまうからです。

**そこで「正しいか」ではなく「どこまで使えるか」を示します。** 確かめられることは四つあります。

1. 自分で置いた約束を、自分で守っているか。ここは機械的に確かめられます。
2. 何が出たら失敗とみなすかを先に決め、反例を探しているか。索引の語句が本文に見つからなければ組み立てを止める仕組みは、その一例です。
3. 表し方が捨てたものを、量で示しているか。どこまでなら捨ててよいかは、道具の外で決めます。
4. 決め方を少し変えたとき、結論がひっくり返らないか。ひっくり返るなら、その決定には大きな荷重がかかっています。そこに印を付けておきます。

範囲の外は「誤り」ではなく「未定義」です。あとで触れる休憩の検出は、作ったデータでは 85% 以上当たっていました。静かな休憩という範囲の中では、正しく働いていたのです。ざわめく本物の休憩は、その範囲の外にありました。決めた表し方は、それ以後に見える違いを縛ります。ですから、決定はいつでも改められる形で置いておきます。

**数字になると、決めたことが見えなくなります。** 指標は、決めた表し方を計算したものです。計算そのものは確かめられます。けれども、何を数えるかを選んだのは人です。数字になると、その選択は客観的な値の陰に隠れてしまいます。文字起こしのエンジンを出力の文字数で比べたとき、ありもしない発話まで「多く書き起こせた」と数えていたのは、このためです。指標がそのまま目標にされると役に立たなくなる、いわゆるグッドハートの法則も、同じところから来ています。そこで指標には、計算の手順だけでなく、どの決定に拠っているかを書き添えます。指標が効かなくなったとき、計算の誤りなのか、決定の限界なのかを切り分けられるからです。

**外から来た制約には、出どころと外れる条件を書いておきます。** 道具には、道具の外で決まった制約が降りてきます。その制約を守ったかどうかは確かめられます。けれども、制約そのものが正しいかどうかは、道具の側からは確かめられません。物差しが外にあり、評価はずっと後にならないと出ず、別の制約だったらどうなったかを比べることもできないからです。そこで、誰のどういう事情から来た制約か、何が変われば外れるのかを記録しておきます。たとえば休憩の検出で多めに拾う設定を既定にしたのは、見逃したときの損が大きいという、使う側の事情によるものです。その事情が変われば、既定値も変わります。

## 人間の受け持ち

*一つ目の問い（目的にかなうか）は、ここでしか答えられません。*

**下書きを直すほうが遅いなら、下書きは要りません。** 長い録画の章立てを、機械に下書きさせたことがあります。確定版との一致は 52.4% でした。半分しか合わない下書きは、結局すべての境界を確かめ直させます。一から打つほうが速かったのです。下書きが役に立つのは、確かめて直す手間が、一から作る手間より小さいときだけです。

**機械は候補を出し、人が決めます。** そこで、機械の検出結果は「候補」として画面に出すだけにしました。人は候補に飛び、前後に動かして位置を詰め、確定します。確定に使うのは候補の時刻ではなく、人が詰めたあとの再生位置です。境界の一秒を決めるのは、人の仕事だからです。

**終わったかどうかは、人が決めます。** 連絡事項のうち済んだものを、日付で自動的に判定しようとしたことがあります。それでは、行事のあとに残る精算や返却を取りこぼしてしまいます。済んだという印は人が付け、道具はそれを畳むだけにしました。消すのではなく畳むので、開けばいつでも読めます。

**作ったデータで通っても、実物で通るまでは使いません。** 休憩を見分ける仕組みは、作ったデータでは 85% 以上当たっていました。ところが実際の 134 分の録画にかけると、ありもしない休憩を 12 か所も見つけてしまいました。作った休憩の音は、ほとんど無音でした。本物の休憩は、ざわめいていたのです。

**既定値は、外したときの損で決めます。** 休憩の検出は、多めに拾う設定を既定にしています。見逃せば、三時間の録画を手で探すことになります。余分な候補は、一回飛ばせば消えます。損が釣り合っていないなら、既定値も釣り合わせないほうがよいのです。

## 目的が道具を選ぶ

パラダイムは参考であって、目的ではありません。目的に合わなければ、外れることもあります。

**結果を、別のファイルではなく PDF の中に埋め込みました。** UNIX の流儀なら、結果はテキストの別ファイルに出すところです。けれどもアンケートの電子化では、PDF を一つ渡せば、別の人がそのまま校正を続けられることが目的でした。そこで結果を PDF の中に埋め込みました。手分けのために分けても、それぞれが一つで完結します。

**あえて画面を持つ道具にしました。** 利用者を画面に縛りつけるな、という教えもあります。けれども、長い録画のどこで区切るかは、波形を見ながら人が決めることです。そのための画面は要ります。その代わり、判断と関係のない書き出しは、画面から外してコマンドに戻しました。

## 振り返ると

道具の作り方そのものは、ほとんど既存のパラダイムに帰着します。一つの仕事を、小さく作って、テキストでつなぐ。これは UNIX の考え方そのものです[^3]。

けれども、何のために作るのか、それで目的にかなっているのかは、どのパラダイムにも書いてありません。それは道具の外にあって、人間が持ち込み、人間が責任を負うものだからです。

ですから、結果が正しいかどうかは、道具の中では最後まで閉じません。言えるのは、入力が健全であったこと、経路が適切であったこと、そしてそれを後からたどれること、の三つまでです。これは弱い主張に見えるかもしれません。けれども、この条件のもとで言えるいちばん強い主張で、しかも反証できます。記録が残っていれば、入力のどこが不健全だったか、どの経路の選び方がまずかったかを、後から指摘できるからです。結果では裁けなくても、やり方は確かめられます。何をもって経路が適切とするかは、あらかじめ合意した手順に拠るほかありません。道具の側が引き受けるのは、その拠り所がどこにあるかを、はっきり示しておくところまでです。
