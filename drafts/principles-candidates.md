# tool-philosophy 書き直し用 — 原則の候補（出典つき）

2026-10-01 作成。**下書き・非公開。** どれを残すか、言葉をどう選ぶかは著者が決める。

## この一覧の作り方

既に実践していることだけを拾った。計画や願望は入れていない。拾い出した素材は次の 3 系統。

| 記号 | 素材 | 中身 |
| --- | --- | --- |
| **V** | Obsidian vault（`01_Ideas` / `00_MOC`） | 考え方。なぜそうするか |
| **I** | 各リポジトリの実装・設計文書・README | 実際にどう作っているか |
| **W** | worklog・`~/.claude/CLAUDE.md`・記憶・skill | 失敗から学んだ実話 |

- 3 系統で計 84 件の候補が出た。重複をまとめて 33 件にした。
- 各項目には、何系統に根拠があるかを ◎（2 系統以上）／○（1 系統）で示す。
- 公開時は、出典のパスを外し、実話の数字だけを残す想定。
- 所属に繋がる出典、講師・団員・依頼主の実名は、この一覧に入れていない。

### 見立て：UNIX 哲学に帰着するが、それだけではない

vault には「UNIX」「配管と陶器」という語が一度も出てこない。

- UNIX 哲学は、**道具の作り方**としてコードの側に表れている（I）。
- vault が語っているのは、**その一つ上の層**である。なぜ分けるのか、何を人が持ち、何を機械に任せるのか、正しさをどう担保するのか。

そこで構成は次の順にする。

1. 実践の原則を並べる。
2. 「振り返ると UNIX 哲学に帰着する」と結ぶ。
3. 帰着しない部分（II）を示す。

UNIX 哲学を冒頭に掲げると、判断が理論の後追いに見えてしまうため、この順にした。

## I. UNIX 哲学に重なる部分 ── 道具の作り方

**1. 一つの道具に一つの目的。レアケースのために恒久的な複雑さを抱えない** ◎（I・W）
- 実話:
  - 「このツールは、同期を取るだけにしたいので、他の機能は不要ですね」
  - 録音の止め忘れ対策は「割に合わない」として入れなかった。
- 作例: media-scribe-workflow には単機能の CLI が 44 本ある（bin/ 21・bin/advanced/ 23）。
- 出典: `media-scribe-workflow/CLAUDE.md`、`worklog/av-sync/2026-07-22.md`

**2. 書くのは接続部だけ。既存を書き換えずに配管として被せる** ◎（I・W）
- 実話: 「車輪の再開発って、避けたいんですね」
- 作例:
  - vision-book-digitizer（解析は Vision に任せている）
  - media-scribe-workflow（ffmpeg / Whisper / LuaTeX を束ねる）
- 出典: 記事 `dont-write-design.md`「書いたのは これらをどう接続するか だけ」、`media-scribe-workflow/worklog/2026-05-17.md`

**3. テキストを界面にし、界面は据え置いて定義だけを差し替える。形式を変える前に、誰が読んでいるかを確かめる** ◎（I・W）
- 実話: `\ts{}` を書き換えたら、下流のダッシュボードで再生が止まった。同じ壊し方を 2 回した。
- 作例: media-scribe-workflow の `tex-link-timestamps`「記法は界面である」
- 出典: `worklog/transcription/2026-08-14.md`

**4. 小さく保ち、依存を増やさない** ○（I）
- 作例: `bin/advanced/` のうち 14 本が「依存: Python 標準ライブラリのみ」。
- 補足: 「書かない設計」は、実際には「外部依存を書き足さない」という意味で運用している（自作の小道具は多い）。

**5. 黙らない。壊れるなら大きな音で壊す** ◎◎（I・W）
- 実話:
  - 終了コード 0 なのに中身が空だった（ASR が segments=0 なのに words.json は 707KB 出ていた）。
  - 別環境の PyInstaller でビルドしたものを配布してしまった（手がかりはサイズ差 61.4MB / 54.6MB だけ）。
  - 索引は本文に実在する語句で指名させ、一致しなければビルドを落とす。これで計 11 箇所の誤指名を捕まえた。
- 作例: iq-analyzer「No silent failures」、media-scribe-workflow（distil モデルの指定は警告して無効化）

**6. 機能が増えたら、コマンドを乱立させず、単一の入口＋モードに畳む** ○（W）
- 作例: SRT 関連の 6 コマンドを、1 本＋モードに統合した。

**7. 移行は、古い方を消して完了する** ◎◎（W・I）
- 理由: 定義が二つ残ると片方だけが育ち、古い方を選んだ瞬間に、修正済みの欠陥が復活する。
- 作例: `.vce.json` を退役させ、章立て `.txt` に一本化した。旧コマンドは退役させた。

## II. UNIX 哲学を超える部分

### II-a. 一次資料と時間 ── 何を確定させ、何を作り直すか

**8. 一次資料は凍結して書き換えない。派生物は、いつでも作り直せるものとして扱う** ◎◎（I・W）
- 作例: media-scribe-workflow
  - 一次資料は、メディア＋`.words.json`＋`.meta.json` の 3 点。
  - SRT は派生物で、校正は派生側で行う。
- 実話: 原本を「編集後」と決めたことで、SRT の時刻を付け直す作業が不要になった。
- 出典: `media-scribe-workflow/CLAUDE.md`

**9. パイプラインに明示的な凍結点を置く。下流はすべてそこから導出する** ◎（I・W）
- 作例: 章立て（Chaptr）を凍結点にしている。「[2] より前は何度でもやり直せる」。
- 出典: `media-scribe-workflow/docs/workflow-rehearsal-to-dashboard.md`

**10. 来歴を残し、既存の一次資料を黙って壊さない** ◎（I・W）
- 作例:
  - meta.json に入力の sha256・エンジン・パラメータを残す。
  - 出力先が既にあれば停止し、上書きは `--force` のときだけ（15 本以上が採用）。
  - enquete は原本を `.bak.pdf` に退避する。

**11. 生成物は手で直さない。数字も説明文も、実データから作る** ◎◎（I・W）
- 実話: 説明文の「紙アンケートのみ」が、226 件のクロス集計まで紙のみだと誤読させた。2 度とも、説明文の側が誤っていた。
- 作例: ダッシュボードの manifest は機械生成のみ（非公開）。公開側では `video-cut-chapters` が章ファイルを再計時して自動で書き出す。

**12. 成果物は単体で自己完結させる** ○（I）
- 作例:
  - enquete は結果を PDF 自身に埋め込み、サイドカーを作らない。
  - book-viewer は見開き・綴じ方向を PDF の標準項目に書き込む。

**13. 正本は一つ。同じものを二箇所に持たない** ◎◎（V・W）
- 作例:
  - 道具ごとに役割を一つに決める（コード / ファイル実体 / DB 可視化 / 知識ネットワーク）。
  - 画像の正本は、各リポジトリの README に置く。

**14. 派生物から一次資料へ、すぐ戻れる導線を残す** ◎◎（W・I）
- 作例: ダッシュボードの全指摘から、動画の該当秒へ飛べる。抽出リストには PDF のページ番号を併記する。

### II-b. 人と機械の分担

**15. 境界と「完了」は人が決める。道具は候補を出し、畳むだけ** ◎◎（V・I・W）
- 作例:
  - Chaptr「境界の 1 秒を決めるのは人の仕事」（検出結果は候補として出すだけ）
  - 連絡事項の [済] は人が付け、道具はそれを畳む（日付による自動判定は、精算や返却の取りこぼしを生む）。
- 考え方（V）: 仕事は考え方と作業からなる。作業は自動化し、人は考え方に集中する。

**16. 下書きが役に立つのは「検証＋修正 < 一から作成」のときだけ** ○（I）
- 実話:
  - 章立ての自動下書きの一致率は 52.4%。結局、人が全境界を検証することになった。
  - もっともらしい誤りに引きずられる（錨効果）。
  - 実測すると、一から作る方が速かった。
- 出典: `media-scribe-workflow/docs/workflow-rehearsal-to-dashboard.md`

**17. 差分は機械が取り、判断だけを人がする。指標は、人の判読を置き換えるためでなく、その誤りを見えるようにするために使う** ◎（I・V）
- 作例: `chapters-diff`「手で反映すると必ず取りこぼす」
- 実話（V）: 指標と突き合わせた結果、14 件が一致し、判読側の誤りが 2 件見つかった。

**18. 確認済みの状態は、編集されたら失効させる** ○（I）
- 作例: enquete（確認済みのページを編集すると確認が外れ、`Esc` で確認時点に戻せる）

**19. 畳めない差異は畳まず、両論を併記する。機械の抽出は補助にとどめ、要所は通読して指名する** ◎（W）
- 実話:
  - 同じ指導が年度によって逆に見えたので、一方に丸めず並べた。
  - ある用語は本文に 39 回出るが、原理を説いているのは 5 箇所だけ。キーワード抽出では質が出ない。

**20. 既定値は、損失の非対称性で決める** ◎（W）
- 実話: 休憩検出の既定は「拾い目」。見逃すと 3 時間の録画を手で走査することになるが、余分な候補はスキップ 1 回で消える。

**21. 最適化してよいのは道具操作の層だけ。思考の層は、常に注意を要する** ○（V）
- 補足: 道具を更新すると、自動化した操作がまた注意の要る作業に戻る。この限界も自覚している。
- 関連（V）: 書くことには 2 種類ある。思考そのものである書記と、思考を中断する書記を混ぜない。

### II-c. 正しさの担保 ── 推論より測定、結果より過程

**22. 推論せず測る。見た目から原因や寸法を推理しない** ◎◎（I・W）
- 実話:
  - 相互相関の符号を逆に読んで、ずれを 24.6ms から 52.3ms に悪化させ、32GB を無駄に書いた。既知量を人工的に入れて符号を確かめる手順に変えると、3.8ms まで追い込めた。
  - スクリーンショットから寸法を推定して、3 回外した。

**23. 単一の数字で判断しない。評価指標を疑う。「該当 0 件」は合格ではない** ◎◎（I・V・W）
- 実話:
  - 文字数で比べると、幻聴の多いエンジンが「最良」になった（幻聴率 21.3%）。
  - 統合ラウドネスは目標どおりなのに、話者だけが 20dB 沈んでいた。
  - 標準の閾値では 0 件だったものが、相対閾値にすると 9 区間検出された。

**24. 同じものを 3 回コピーしても、証拠は 3 つにならない。検算は、作った規則と独立した基準で行う** ◎（V・W）
- 実話: 6 本の書き起こしを突き合わせたが、実は「2 系統×書式違い」だった。

**25. 合成テストは実素材と同じ条件に置き、実素材で通るまで採用しない** ◎（W・I）
- 実話: 休憩判別は合成データで 85% だったが、実録画では休憩を 12 個捏造した（合成の休憩音が実質無音だったため）。

**26. 正しいものを作ったかは確かめきれない。だから、どう作ったかを誰でも追える状態を保証する** ◎（V・I）
- 考え方（V）:
  - 「正しく作ったか」は確認できるが、「正しいものを作ったか」は原理的に確認しきれない（V&V の非対称性）。
  - 「誤りがあれば特定し修正できる」状態は保証できる。
  - 決めることと責任を負うことを同時にする。トレーサビリティなくして責任は付随しえない。
- 実践: 来歴（10）、一次資料への導線（14）、worklog、vault の「## 変遷」節。
- 注: 「結果の妥当性が言えないなら過程の妥当性で担保する」という直接の言い回しは、出典が非公開文脈のため使わない。この項の表現で言い換える。

**27. 確かでない箇所は、確かでないと明示する（追い込まず、隠さない）** ◎◎（W・V）
- 作例: 時刻が推定のものには「≈」を付けて表示する。断定できないものは「要確認」に回す。対話から生まれた概念には出自と「未検証の範囲」を書く。

### II-d. 運用

**28. 不可逆な一括操作は、対象と対象外の件数を数え、undo ログを先に書き、実行後は成功件数と実ファイル数を突き合わせる** ◎◎（W）
- 実話:
  - 無関係な 97 件が巻き込まれる寸前だった。
  - 26 件成功の表示に対して、実ファイルは 24 本だった（上書きによる消失）。

**29. 段階的に出す（1 件 → 全件、予行演習）。一度に変える変数は一つだけ** ◎◎（W・V）
- 作例: 記事の投入は「1 件 → リンク付き 1 件 → 全件」。リリース前にドラフトで予行演習する。PID 制御は P 制御だけで動かしてから広げた。

**30. 新しく提案する前に、過去の決定と既存資産を棚卸しする** ◎◎（W）
- 実話: 2 日前に決めたエンジンを忘れて、別のものを提案してしまった。
- 作例: worklog を自動参照する仕組み。

**31. 知見は抽象度ごとに置き場を分ける。全体へ上げるのは 3 条件を満たすものだけで、人の承認を経る** ◎◎（W・V）
- 作例:
  - 記憶の階層の表（worklog / 案件メモリ / 全体記憶 / 思想 / 行動規範 / 手順）。
  - vault の Ideas / References / Sources の分離。

**32. どこで切ったか、なぜ切ったか、切った先に何を残したかを記録する（射程外は排除ではなく保全）** ◎（V・W）
- 作例: worklog の「検討して採らなかった選択肢と理由」節。

**33. 私的な領域は自動化しない。外部の無料基盤はいずれ消える前提で、差し替え点を 1 関数に閉じ込める** ◎（W）
- 実話:
  - LINE の自動取り込みは見送った（会話の私的さが変わるため）。
  - 無料の LLM 基盤が 1 年たたずに廃止されたが、移行は 1 関数で済んだ。

## 書き直しの前に片付けたい、文書と実践の食い違い

公開文書が実態と食い違っていると、この文書の信用も落ちる。

1. **Chaptr の README（main）が、撤去済みの機能を宣伝している**
   - 書かれている機能: GPU エンコード・書き出し・焼き込み
   - 撤去したコミット: `f3f9585`（2026-09-07）
2. **chaptr/CLAUDE.md が、media-scribe-workflow の旧 CLAUDE.md のコピーのまま**
3. **`.vce.json` を退役させたのに、文書が追従していない**
   - 対象: `DESIGN_PRINCIPLES.md` §3、記事 `tools-and-orchestrator`
4. **記事にあって、実装に無いもの**
   - Makefile による骨格、PDF/A での配布
   - 実際のオーケストレーターは、YAML 駆動の Python
5. **SRT の位置づけが変わった**
   - 記事: 「段階間の標準インターフェース」
   - 実践: 「派生物」（一次資料は words.json＋meta.json）
6. **現行の tool-philosophy 自体が、実際のリポジトリと一致していない**
   - 文書の命名規則: `plumb-*` / `mid-*`
   - 実際: `msw-*`、`yt-srt` など
